# PHASE 14 — Second-pass novelty

Do not repeat the first-pass checklist. Ask: what would an experienced protocol designer least expect an attacker to do?

Unusual sequences, boundary values, temporary states, cross-market actions that look irrational until composed, config changes around existing positions, repeated tiny operations, unexpected token semantics, inherited external-protocol assumptions.

**Revisit every `SELF_RESOLVED` lead.** Confirmation bias when closing a lead is as dangerous as anchoring when opening one. Where feasible, upgrade the closure to an empirical check. Where not, record why the original reasoning still holds.
